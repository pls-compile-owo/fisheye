## 快速开始

```bash
# 1. 铺网（自动规划预算与密度）
node fisheye.mjs auto <BV> --budget 20000

# 只处理某一段 / 某个分P
node fisheye.mjs auto <BV> --from 5:30 --to 8:00 --budget 8000
node fisheye.mjs auto <BV> --p 2 --from 1:00 --to 3:00

# 2. 精读（三选一）
node fisheye.mjs refine <BV> --template                      # 生成决策模板
node fisheye.mjs refine <BV> --decisions <file.json>         # 按读图判断精读
node fisheye.mjs refine <BV>                                 # 几何兜底（零 token）

# 手动控制
node fisheye.mjs grid <BV> --chunk 60 --grid 3x3 [--from] [--to] [--p]
node fisheye.mjs subs <BV> --count 14 [--from] [--to] [--p]
node fisheye.mjs grab <BV> 69.6,75.3 [--p]
```

时间参数三种写法：`330`（秒）/ `5:30` / `1:05:30`。只给 `--from` 会自动到片尾。
分P：`--p N`（默认 1），cache 按 `BV-P2.mp4` 区分，manifest 记 `page` 供 refine 找对缓存。

辅助脚本：`analyze_subs.py`（字幕带自动定位）、`check-subs.mjs`（查官方字幕轨）、`pick.js`（挑测试视频）

依赖：ffmpeg（自动找 `~/.dsh/surfcore/bili/bin/ffmpeg.exe`）、B 站 credentials、Python + Pillow

## 精读点自动选择

核心分工：**语义判断只有读图能做，几何判断可以纯计算**。

| 判断 | 谁做 | 成本 |
|---|---|---|
| 「这格重要吗、看不看得清」 | 读图的模型 | 已经付过（看拼图） |
| 「这格的字在拼图里还剩几像素」 | 脚本 | 0 |
| 「这格画面变化多剧烈」 | 脚本 | 0 |

`refine` 三种模式：

### `--template` —— 生成决策模板

给每格一行，模型读完拼图后填 `desc` / `needDetail` / `reason`：

```json
{"chunk": 2, "cell": 9, "t": 79.9, "ts": "01:19", "scene": 0.793,
 "desc": "商业街特写，背景有海报", "needDetail": true,
 "reason": "海报上的字拼图里读不全"}
```

### `--decisions` —— 按判断自动截

只处理 `needDetail=true` 的格，打印每个点的理由，自动调 `grab`，并报告精读成本。
容错：自动去掉 BOM（PowerShell 的 `Set-Content -Encoding UTF8` 和记事本都会加）。

### 无参数 —— 几何兜底

不读图，纯计算：

- 字幕在拼图里的像素高度 < 12px 时，判定「必然糊」——**但只在没有字幕带时才逐帧精读**（有字幕带的话字幕已被单独读掉，不必重复）
- 画面变化强度 ≥ 0.85
- 按强度排序取前 6 个

### 实测：几何兜底 vs 模型判断，选出完全不同的点

82 秒 MV 的对比：

| | 选中的点 | 理由 |
|---|---|---|
| **几何兜底** | 01:09 (0.991)、01:15 (0.895) | 画面变化最剧烈——但实际是**转场闪白** |
| **模型判断** | 01:19、00:01 | 海报文字读不清、暗部细节不明 |

**两种选择完全不重合。** 因为「变化剧烈」和「信息量大」是两回事，而「有文字」这个信号几何方法根本看不见。

这也说明：几何兜底是安全网，不是替代品。

## 实测案例

### 案例 1：01:19 商业街海报

- 拼图里：只能看到「WAT MERC...」的模糊轮廓
- 精读后：完整读出「**WAGYU MERC KATSU**」——背景是商业街的和牛炸牛排店招牌

### 案例 2：00:01 暗巷

- 拼图里：只能看出是暗色巷子
- 精读后：确认是日式小巷入口，有外卖摩托（蓝色保温箱带图案）、左侧镜子招牌、地上堆着纸箱杂物

### 踩到的坑：时间精度不够会跨镜头

manifest 最初只存 1 位小数（`t=1.7`），但真实帧是 `1.73`。
这条视频恰好在 **1.70~1.73 之间有一个切点**——拼图用 1.73 取到暗巷，精读用 1.7 就跑到下一个逆光镜头了。

看起来像「seek 偏差 1 秒」，实际是精度丢失。改成存 2 位小数后完全一致。

**教训：时间戳精度必须高于镜头切换的最小间隔。**

## 信息源优先级（三条腿，从省到贵）

原本只做了「画面」这一条腿，验证官方字幕时发现缺口并补上：

| 优先级 | 信息源 | 成本 | 什么时候用 |
|---|---|---|---|
| 1 | **官方字幕**（`getOfficialSubs`） | ≈ 字数 token（489 字 ≈ 489 token） | 视频有官方/AI 字幕轨 |
| 2 | **烧录字幕带**（`subs --auto`） | 1 张图 ≈ 1000 token | 字幕烧进画面、无官方轨 |
| 3 | **只靠画面拼图** | 按密度算 | 无任何字幕 |

实现要点：

- 官方字幕走 WBI 签名 `/x/player/wbi/v2`（旧端点拿到的 URL 缺 `auth_key` → CDN 403），`auth_key` 分钟级过期需立即下载，匿名拿不到 AI 字幕必须带 cookie
- **官方字幕要先过质量判断**：B 站 AI 字幕在纯音乐/音效视频里会输出大量「♪ 歌词」噪声或碎片，拿去当台词会让理解完全跑偏。判据：平均有效字数（去掉 ♪ 和空白）< 2 字/行，或去重率 < 0.4 → 判定噪声，降级看画面
- 拿到可用官方字幕就**跳过字幕带**，manifest 记 `subsSource: 'official' | 'burned-in' | null` 和 `subsCovered`
- `geometricPick` 用 `subsCovered` 判断「字幕糊是否值得精读」——字幕信息已覆盖就不必为它逐帧精读
- 字幕超过 8000 字会提示「建议只读关心的时段」，避免长视频 ASR 字幕把上下文撑爆

### 实测对比（同一条视频 BV1ziWP6qENy）

| 方案 | 成本 | 信息量 |
|---|---|---|
| 旧（字幕带） | 1000 token | 抽 14 行字幕，OCR 有误 |
| 新（官方字幕） | **489 token** | **完整 50 行**，无 OCR 误差 |

不只是省一半 token，**信息完整度反而更高**。

### 两条腿互补的实例

这条视频标题叫「这是我等待了一生的巨浪」，实际是**英雄联盟比赛集锦（BLG vs T1）**——标题是隐喻。

- 官方字幕给出画面里没有的：解说员实时评论（"BLG team has stolen the Rift Herald"、选手走位评价）
- 拼图给出字幕里没有的：比赛画面、比分（BLG 0:0 T1）、选手名单（Faker/Oner/Doran/Gumayusi）

**字幕 = 听觉信息，拼图 = 视觉信息，谁也替不了谁。**

## 平衡策略：怎么决定花多少

核心问题不是「抽多少帧」，而是**「这个视频看懂需要多密，预算够不够维持这个密度」**。

`auto` 的决策顺序：

```
1. 算内容变化率（显著画面变化 ÷ 时长）
      ↓
2. 按变化率定「看懂所需的最低帧间隔」
   快剪/MV  >1.2 次/秒 → ≤4s/帧
   vlog/教程 >0.5      → ≤6s/帧
   口播/慢节奏 >0.15   → ≤9s/帧
   静态/录屏  其余      → ≤13s/帧
      ↓
3. 张数 = 需要多少帧 ÷ 9
      ↓
4. 预算只用来「封顶」：超出预算才降级，并明确报告降了多少
      ↓
5. 精读不自动做，只给 top-3 建议（大部分视频不需要）
```

**设计原则：密度优先，预算兜底。** 省钱不该靠偷偷把视频抽稀，而该靠判断哪些视频真的不需要密。

成本估算常量：拼图 1200 token/张，字幕带 1000/张，精读 1300/帧。

## 关键技术决策（都踩过坑）

### 1. 取帧：等间隔骨架 + 吸附变化点 + 阈值阶梯 + 去重

```js
基准点 = from + ((i + 0.5) * dur) / n     // 窗口恰好铺满整段，不越界
half  = dur / n / 2                        // 每帧的吸附半径
```

- **只等间隔**会漏掉「只闪一两秒的关键画面」
- **只吸附变化点**会让转场全挤在开头，中段几十秒空档
- **阈值阶梯**：从 0.3 起，≥75% 帧吸附成功就停（段短时窗口小，过半门槛太松）
- **去重**：吸附后相邻两帧若挤得比 `0.4×格距` 还近，后一个退回基准点

一次解码拿全部 `scene_score`（阈值放 0.05），阈值阶梯在内存做 —— 替代了「每个阈值重跑一遍全片解码」。

### 2. 字幕带自动定位（不靠 OCR）

靠「字幕位置固定、每帧都在」这个特性：

1. 抽 24 帧，每帧只看底部 45%，按行算水平梯度（文字=高频边缘）
2. 跨帧取 **30 分位** —— 字幕每帧都强，偶发画面细节被压掉
3. **找峰值**而不是套绝对阈值 —— 字幕是局部尖峰，画面平台会抢先命中（第一次就败在这）
4. 从峰向两侧扩展，允许 25 行间隙（中英文两行之间隔 20~30px），上下留 3px 余量

实测两个视频检出**不同位置**（82–90% / 88–95%），硬编码比例不可能同时适配。

### 3. 快速 seek

**拼图和精读统一用** `-ss` 放在 `-i` 前面（跳到最近关键帧，比精确 seek 快一个数量级）。

统一而不是让精读用精确 seek，是因为工作流是「从拼图挑格子」——**格子的身份比绝对秒数重要**。两边用同一种 seek，才能保证「拼图第 N 格」和「精读同一时间点」是同一帧。

**效果：361 秒视频从 5 分钟+ 降到 33 秒**（含下载；视频已缓存时约 10 秒）。

### 4. 尾段合并

尾段短于 `min(20s, chunk×0.25)` 就并进上一段，避免 361s 在 chunk=120 时多出一张「06:00-06:01」全是同一秒的废图。

### 5. 沙箱管道限制

`execFileSync` 捕获子进程 stdout 直接 EPERM，异常被 catch 吞掉后表现为「静默返回空」——这是最早场景检测返回 0 处的原因。
所有子进程走 `stdio: 'ignore'`，数据一律通过临时文件传递。

## 健壮性（两轮检查修的）

### 第一轮：异常路径与可移植性

| 问题 | 后果 | 修法 |
|---|---|---|
| 路径写死绝对路径 | 换机器/改目录直接废 | 工作区按脚本位置推断；ffmpeg / credentials / python 支持 `FFMPEG` / `BILI_CRED` / `PYTHON` 环境变量覆盖，缺失时明确报错退出 |
| `detectBand` 抛异常没接住 | Python 缺失时整个 auto 崩 | 内部捕获 → 降级为「无字幕」并告警，流程继续 |
| 单帧抽帧失败没接住 | 时间越界 / 解码出错时脚本崩 | 统一走 `grabFrame()`，失败返回 false 不抛异常 |
| 缺帧导致 tile 报错 | 少一帧整段拼图失败 | 缺帧用前一帧补齐；整段不足则跳过并告警，不影响其他段 |
| 空时间点解析成 0 秒 | `grab ""` 会截 00:00 | `Number('') === 0` 陷阱：先滤空串再转换 |
| 精读时间点越界 | 越界点静默抽不到帧 | `refine` 校验 `0 ≤ t ≤ duration`，越界点列出来并忽略 |
| 旧版 manifest 缺几何字段 | 几何兜底读到 undefined | 字段缺失时跳过字幕规则，仅按变化强度挑（已验证） |
| 未捕获异常甩堆栈 | 用户看到一屏红字 | 顶层 try/catch 只输出一行错误；`FISHEYE_DEBUG=1` 才显示堆栈 |

### 第二轮：参数边界、并发与网络

| 问题 | 后果 | 修法 |
|---|---|---|
| `--chunk 0` | `Math.ceil(duration/0)` = Infinity → **死循环** | 所有参数 CLI 统一校验：chunk 1~3600、grid 格式 `NxM`、budget 2000~200000、count 1~50、density 0.5~60、band 0~0.6 |
| `--grid 0x0` / `3x` | N=0 / NaN → tile 报错、行号变 NaN | 同上，grid 必须 `1~9 x 1~9` |
| 下载中断 | 半个 mp4 被当成缓存，以后每次都拿残缺文件跑 | 下载到 `.part` 再 rename；内容过短（<1KB）丢弃；下次自动重下 |
| fetch 无超时 | 网络卡住时**无限挂起** | API 15s / 下载 5min 超时（`AbortSignal.timeout`） |
| `.scenes.txt` 固定文件名 | 两个视频并发跑互相覆盖 | 临时文件名加 pid + 时间戳 |
| 取元信息三处重复且漏查 code | 无效 BV 时有的路径崩得不明不白 | 统一 `getView()`（带超时 + code 校验） |
| 预算低于最低配置 | 报告 estTotal 4800 但预算只有 2000，没有解释 | 明确警告「最低配置已要 X token，超出预算，将超支运行」 |

### 已验证的降级路径

- Python 缺失 → 告警一次，按无字幕继续跑完
- 无 manifest → `错误：没有 manifest，先跑 auto 或 grid：<路径>`
- 空/非法时间点 → `没有有效时间点（格式：44,59.5,79.9）`
- 未知阶段 → `未知阶段: xxx`，退出码 2
- 全部非法参数 → `参数错误：<原因>`，退出码 2（不会再死循环/NaN 连环）
- 预算 2000 跑 361s → 自动降为 1 张（40.1s/帧）+ 明确降级与超支警告

## 逻辑优化（第三轮：只改设计，不修 bug）

| # | 改动 | 理由 | 实测 |
|---|---|---|---|
| 1 | `grab` 文件名 1 位小数 → 2 位 | `t=1.73` 和 `1.74` 都会写成 `grab-1_7s.jpg`，后一个**覆盖**前一个 | 两帧同时生成，不再冲突 |
| 2 | 字幕行从纯等间隔改为**吸附变化点** | 字幕在镜头切换时更新，纯等间隔的第 1 行常是「还没出字幕」的空帧 | 第 1 行 00:02 → 00:04，多行落到变化点上 |
| 3 | `detectBand` 抽帧从 `fps` 滤镜改为**逐帧快速 seek** | `fps` 滤镜输出 24 帧但必须**全片解码**，长视频慢一个数量级 | 361s 总耗时 33s → 26s |
| 4 | 吸附从「最近变化点」改为「**最剧烈**变化点」 | 窗口内多个变化点时，时间代表性由窗口保证，应取视觉上最显著的时刻 | 触发去重兜底，输出正常 |
| 5 | 场景检测降到 **320p** 计算 | scene score 是归一化的像素差均值，对分辨率不敏感 | 候选 669→667（-0.3%），≥0.15 的 228→223（-2.2%），几乎零损失 |
| 6 | auto 的精读建议**复用** refine 几何兜底 | 原来两处各维护一套「该精读哪格」的规则，必然漂移 | 两边输出完全一致（同为 4 个时间点） |
| 7 | subs 最后的 crop/tile 加容错 | 拼接失败不该让整个流程崩 | 失败告警并返回 null，不影响拼图 |

## 补充（第四轮：真实使用的盲区）

| # | 缺口 | 为什么重要 | 处理 |
|---|---|---|---|
| 1 | 官方字幕**不判断质量** | ASR 在纯音乐视频里输出 ♪ 噪声，当台词理解会全错 | 平均有效字数 < 2/行 或去重率 < 0.4 → 判噪声，降级看画面 |
| 2 | **竖屏/方形视频 token 估算严重偏低** | 拼图面积按 1920×1080 估 1200 token，方形实际 2133（+78%），竖屏 +3 倍 | 用 `view.dimension` 按面积修正，偏差 >25% 时明示 |
| 3 | 长视频官方字幕**无长度上限** | 1 小时 ASR 字幕可能几万字，全读爆上下文 | 超过 8000 字提示「只读关心的时段」 |
| 4 | **多 P 视频静默只处理 P1** | 合集类会被误读成「整条视频就这些内容」 | 检出 pages>1 时明确告警只处理 P1 |
| 5 | `--decisions` 标记过多无提示 | agent 标 50 格 = 6.5 万 token | 超过 8 帧告警建议先精简 |

实测（方形 LOL 视频）：

```
[比例] 画面 1920x1920 → 拼图 1920x1920，单张约 2133 token（基准 1200 已按面积修正）
[字幕] 官方中文 50 行 / 377 字 ≈ 377 token → 跳过字幕带
[预算] 20000 token ≈ 字幕带 377 + 拼图 4266 + 精读预留 2600 = 7243   ← 修正前误报 5489
```

**这个修正说明了估算的价值**：修正前以为只要 5489，实际 7243，差 32%。

## 补充（第五轮：时间范围与分P）

| 能力 | 实现 | 实测 |
|---|---|---|
| **`--from/--to`** | 内部计算全用「区间长度」，对外（manifest/日志/精读）用全局秒数；场景过滤、字幕过滤、字幕带、拼图全部按区间 | 82s 视频只处理 00:30-01:00 → 1 张拼图 / 4800 token |
| **`--p N`** | 按 `pages[N-1].cid` 取播放地址，cache 按 `BV-p2.mp4` 区分，manifest 记 `page` | 7P 股票课程 P2（429s）正确下载、标题显示 `· P2/7` |
| 组合 | `--p 2 --from 1:00 --to 3:00` | 120s 区间 / 583 token 字幕 / 2 张拼图 |

### 踩到的坑：字幕位置检测不能只看区间

区间处理时我顺手让 `detectBand` 只在 `[from,to]` 内采样，结果字幕带位置从 **82%-90% 跑偏成 55%-83%**。

原因：**字幕位置是视频级属性**，区间内若恰好多帧没有字幕，峰值就会被画面自身边缘抢走。
修法：采样**始终跨全片**，只有「用哪些时间点抽字幕行」才受区间限制。

这个 bug 还有个隐蔽之处：我改了 `detectBand` 的签名，但 `auto` 里调用时传的是**区间长度** `duration`（30s）而不是全片时长（82s）——两处都没对上才引起漂移。教训：**同一函数的多个调用点必须逐个核对参数语义**。

### 多P 的连带修复

`stageGrid` 里 `fullDuration` 原来取 `view.duration`，多P 视频那是**全部分P 总和**（4398s），不是当前 P 的时长（429s），密度决策会全错。改成 `pages[p-1].duration`。

## 补充（第六轮：竖屏视频字幕带翻车）

真实使用中用户拿一条**竖屏 1080×1920 猫狗混剪**（BV12F411E7Zi）测试，发现字幕带里 14 行只有 3 行是字幕，其余全是画面中部内容。

**根因**：抖音式动态字幕——位置漂移、不是每帧都有。旧算法的阈值扩展在竖屏高分辨率下把画面内容整片连进了"字幕带"（检测出 531px 高，实际字幕只有 ~60px）。

**修法两处**：

1. **高度上限**：字幕带不超过搜索区的 1/4，超限收敛到峰值附近（实测 531px → 222px）
2. **置信度门槛**：算「字幕区每帧强度 vs 该帧画面自身强度」（用 75 分位而非 mean——字幕只占几十像素，mean 会被画面稀释，实测得 0.00）。低于 0.5 判定字幕不规律，跳过字幕带

**验证（关键是不误伤）**：

| 视频 | 检测 | 置信度 | 决策 |
|---|---|---|---|
| 横屏 MV（固定底部字幕） | 82%-90% | **0.63** | ✓ 采用 |
| 竖屏猫狗（动态字幕） | 60%-72% | **0.29** | ✓ 拒绝 |

**遗留局限**：`scene score` 只测像素变化，抓不到「同场景内的叙事切换」——这条混剪变化率只有 0.13/秒被判为"慢"，于是只给 1 张拼图（12 秒/帧）。觉得漏内容可以用 `--density 4` 手动加密。

## 补充（第七轮：接入弹幕，第三个信息源）

2026-11-11 晚加：`getDanmaku()` + `summarizeDanmaku()`（约 108 行）。

**为什么值得加**：弹幕能看到画面和字幕里都没有的东西——**观众在哪一秒最激动**。这正好补上几何规则的盲区（几何只能找「画面变化剧烈」）。

**实现**：
1. 拉 `<cid>.xml`（`https://comment.bilibili.com/<cid>.xml`）
2. 解析 `<d p="相对秒,...">内容</d>`，只取时间和文本
3. 按 **5 秒桶**聚合，按密度取最热的 6 个桶
4. 每个热区取**出现次数最多的 3 条**（高频重复 = 那里在刷的梗）

**闭环**：热区写进 `manifest.danmaku.hot` → `refine` 的几何兜底会合并它 → 精读能截到「观众最激动的那一帧」。

**实测效果（这是最有说服力的部分）**：

| 视频 | 热区 | 弹幕内容 | 说明 |
|---|---|---|---|
| LOL（335 条） | 01:20-01:30（36/35/37 条） | 「打破桎梏×8」「翻山覆海×4」+ "压抑到极致后的爆发" | 团战高潮 |
| 何同学 vlog（828 条） | 02:55-03:05（43/45/30 条） | **清一色「？」「？？」「啊？」** | 那里有个意外转折 |

第二种是几何规则**永远发现不了**的：画面变化可能不大，但观众集体懵了——那就是视频的爆点。

**踩到的两个坑**：
1. `manifest` 里没有弹幕字段时 `refine` 用不上 → 必须把 `dmHot` 通过 `pre` 传进 `stageGrid`
2. 热区的 `ts` 用桶起点、`t` 用桶中点，导致排序后显示错乱（01:22 跑到 01:20 前面）→ 统一用中点
3. 去重按 `Math.round(t)` 不够狠（82.18 和 82.5 都显示 01:22 却没去重）→ 改 `Math.floor`

### 弹幕也参与铺网取帧（默认开）

用户提出：B 站的网站特点就是弹幕数量能影响内容判断——那些「画面没怎么变、但观众集体激动」的时刻，纯视觉检测抓不到。所以让弹幕热区也进入 `pickTimes` 的吸附候选。

**关键设计：score 给 0.9，不是 1.0**
- 同一窗口里真实画面变化（1.0）优先
- 一个热区不会把整段的帧全吸过去，不破坏均匀覆盖

**代码结构上必须分离两个数组**：

| 变量 | 用途 | 是否含弹幕 |
|---|---|---|
| `visualScenes` | manifest 每格的 `scene` 分数、场景统计日志 | ❌ 纯画面 |
| `sceneCands` | `pickTimes` 的吸附候选 | ✅ 画面 + 弹幕热区 |

否则 manifest 里 `scene: 0.9` 会混进弹幕的分数，误导"这格画面变化剧烈"的判断。

**实测对比（同一条 LOL 视频）**：

| 配置 | 段1 吸附数 | 帧位置变化 |
|---|---|---|
| 默认（弹幕参与） | **3/9** | #5 从 00:28 → 00:27（吸到热区中点） |
| `--no-danmaku-frames` | 2/9 | 保持纯画面 |

影响是**温和的**：多吸 1 帧、微调 1 秒，其他帧位置不动。这正是 score 0.9 的效果。

开关：`--no-danmaku-frames`（不用弹幕参与取帧）。

| 被误杀的弹幕 | 误判原因 | 教训 |

| 「**？？？**」 | 纯符号判定 | 问号/感叹号/省略号是 B 站最典型的反应弹幕 |

```

  私信引流   私信我/私我
  主页引流   关注我/我的主页/简介有
  诈骗话术   免费送/白嫖领
  链接       http(s):// / www.
  标价       ¥数字 / 数字元起
  联系方式   7~11 位连续数字

噪声（3 条）：
  纯符号     完全不含字母数字（且不是情绪标点）
  重复刷屏   单字符重复 4+ 次，**且必须是字母**（aaaa 过滤，66666 保留）
```

**保留**：`666` `66666` `1111` `awsl` `哈哈哈哈` `？？？` `!!!` `……` `¿` `前面的说得对` `看这个场面` `找我妈`…

## 补充（第九轮：真实案例 BV1i4W86zEUS —— 超长视频 + 视频内广告段）

用户给小约翰可汗《如何盗走蒙娜丽莎》（**BV1i4W86zEUS，39.7 分钟**，3600 条弹幕），并指认 **04:35-06:49 是鱼油广告**。这个案例同时暴露了两件事。

### 发现一：超长视频触及张数上限

```
[下载] 2385s → 234.89 MB
[内容] 显著变化 545 处，变化率 0.23 次/秒
[字幕] 官方中文 1283 行 / 12410 字 ≈ 12410 token   ← 光字幕就吃掉 40% 预算
[密度] 目标 ≤9s/帧
[张数] 密度需要 30 张，预算允许 12 张 → 采用 12 张
[降级] 实际 22.1s/帧，稀于目标 9s/帧
```

**问题**：广告段（2分14秒）落在「图2」里，占掉 6/9 格。**它白白吃掉了拼图预算。**

### 发现二：广告段可以被弹幕识别

用户指认的广告段，弹幕数据长这样：

```
全片每 20 秒平均 30.0 条
广告段平均 9.8 条  ← 只有 31%
  4:40→5  5:00→3  5:20→3  5:40→4  6:00→2  6:20→11  6:40→22（恢复）
```

**广告段是一条清晰的弹幕密度低谷**（观众跳过 / 不互动）。加上关键词：

```
6:40  感谢金主爸爸，请大家给予除了购买产品之外的一切帮助
6:43  感谢金主爸爸催更
4:43  B站一提到鱼油我就知道是海力生了
```

### 实现：`detectAdSegments()`

```
1. 30 秒滑窗（步长 10s）算弹幕密度
2. 低于中位数 45% 的窗口 → 合并成区间（≥60s 才保留）
3. 附近 ±20s 有广告关键词（金主/恰饭/商单/赞助/带货…）→ confidence='high'
   没有关键词 → confidence='low'（低互动段，未必是广告）
```

**分级的意义**：只靠密度会误报（纯画面段、BGM 段也是低谷）。实测这条视频：

| 检测结果 | 置信 | 判断 |
|---|---|---|
| 04:40-06:40（120s，密度低 34%）| **high** | ✅ 真广告（关键词「感谢金主爸爸」）|
| 31:10-32:40（90s，密度低 -25%）| low | 低互动段，非广告 |

**验证：算法检测 04:40-06:40，用户指认 04:35-06:49，误差 5 秒。**

### 精读会避开高置信度广告段

`geometricPick` 里过滤掉 `confidence='high'` 区间内的点：

```
[精读] 选中 8 个时间点：
  00:02  弹幕热区
  01:45  图1 #5 几何规则
  14:34  图5 #4 几何规则
  ...（04:40-06:40 区间内没有任何精读点）
```

**但铺网不完全跳过广告段**——那是有意的：拼图保持时间覆盖，不擅自删内容；只是不鼓励把精读 token 花在广告上。

### 局限

- **依赖弹幕**：无弹幕 / 弹幕关闭的视频检测不到
- **密度低谷会误报**：所以分了 high/low 两级，low 不标广告
- **依赖 UP 主风格**：这个案例里观众是"跳过广告"（密度降）；但也可能有观众"刷屏吐槽广告"（密度升），那种就检测不到
- 234MB 缓存：长视频很占空间，需要定期清 `cache/`

### 广告段不占帧（2026-11-11 晚，用户要求）

检测到 high 置信度广告段后，**把这些时间从铺网里让出来，多分给内容**。

**实现：把广告段从时间轴上「压缩掉」，剩余有效时间重新均分**

```js
pickTimes(from, to, n, scenes, adHigh)
  1. subtractAds(from, to, adHigh) → 剩余连续区间
  2. 在「有效总时长」上等间隔取 n 个基准点（广告时间被压缩掉）
  3. 吸附候选也排除广告段（否则帧会被吸到广告里的高变化点）
  4. half / minGap 用有效时长算（不是原始段长）
```

**效果（BV1i4W86zEUS 图2）**：

| | 广告前 | 广告后 |
|---|---|---|
| 图2 覆盖 | 199s 塞 9 帧 | 跳过 118s 广告后，9 帧只覆盖 81s 内容 |
| 平均间隔 | 22.1s/帧 | **8.3s/帧**（密度提升 2.7 倍）|
| 帧落广告内 | 有 | **0 个** |
| 拼图内容 | 含鱼油广告 | 9 格全是博物馆剧情，第 9 格停在广告前 9 秒 |

**踩的坑**：第一版 `half`/`minGap` 还用原始 `dur` 算，吸附窗口过大 → 9 帧里 5 帧被去重退回。改成用有效时长后回到 1 帧退回。

**manifest 现在会标注**：

```json
{
  "range": "03:18-06:37",
  "adSkipped": 118,
  "effectiveRange": "03:24-04:31"    ← 实际内容覆盖范围

```

日志也说明：`[拼图 2/12] 03:18-06:37  9 帧（跳过广告 118s，内容实际 03:24-04:31）`

**极端情况**：如果某段整段都是广告，跳过这张图（不让它浪费预算）。

**局限**：只跳过 `confidence='high'` 的段；`low`（只有密度低谷、无关键词）不跳——那可能是纯画面/慢镜头段，贸然跳过会丢内容。

## 补充（第十轮：fisheye 自检 `selftest`）

```bash
node fisheye.mjs selftest          # 基础：依赖 / 凭证 / API / 缓存 / 磁盘（0.6 秒）
node fisheye.mjs selftest --deep   # 加深：实测抽帧 + 字幕带定位（1.5 秒）
```

**设计原则**：默认**不下载视频**、几秒内跑完，不产生副作用（临时文件自己删）。

**检查项（12 项）**：

| 类别 | 检查 |
|---|---|
| 依赖 | Node ≥18 · ffmpeg 存在且**真能执行** · python · analyze_subs.py |
| 环境 | 输出目录可写 |
| 凭证 | credentials.json 的 sessdata/bili_jct |
| API | 视频 API（getView）· 弹幕 API · 官方字幕 API |
| 资源 | 缓存（几个视频/多少 MB）· 磁盘剩余 |
| `--deep` | 实测抽帧（用缓存里的视频）· 实测字幕带定位 |

**实际输出**：

```

  [OK] python             Python 3.12.14

  [OK] 弹幕 API           1 条（含广告过滤前）

结果：12 项通过 / 1 项跳过（1.5s）
```

**实现上的两个细节**：

1. **自检要能诊断「依赖缺失」本身**——脚本顶部原本有硬退出（ffmpeg/凭证不存在就 exit 2），selftest 时跳过它，否则自检根本跑不到能报告问题的地方。
2. **子进程输出走文件不走管道**（沙箱禁管道捕获）——`runCapture()` 把 stdout 写临时文件再读，和 `detectScenes` 用的是同一套做法。

**失败时的提示**：

```
怎么修：
  · ffmpeg/python 缺失 → 用环境变量指定路径：FFMPEG=/path/to/ffmpeg.exe  PYTHON=...
  · 凭证缺失         → 在 B 站登录态文件里补 sessdata / bili_jct
  · API 失败         → 检查网络；bilibili 接口可能改了，需要更新代码
  · 字幕带失败       → 确认 python 有 numpy + Pillow
```

**测试视频的选法**：优先用 `cache/` 里已有的视频（不额外请求），没有才用默认 BV；这样自检不会因为某条视频被删而误报。

## 已知局限

- 字幕检测依赖「字幕位置固定」：竖屏、动态字幕、随镜头漂移的会失效
- 变化率只统计「画面切换强度」，不理解语义（讲话画面切得快 ≠ 信息多）
- 精读的语义判断仍需模型读图；纯几何兜底只能找「变化剧烈」，找不出「有文字」
- 时间精度靠 manifest 的 2 位小数，极端快剪（切点密集到 0.1 秒级）仍可能错位
- `grab` 只能截单帧，不能截区间
- 张数硬上限 12，超长视频会触及
- 辅助脚本 `check-subs.mjs` / `pick.js` 里仍留着本机路径（它们只是测试工具，不进主流程）
