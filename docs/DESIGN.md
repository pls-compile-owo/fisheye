# 设计决策

English: [DESIGN.en.md](./DESIGN.en.md)

> 这份文档解释 fisheye 为什么这么做。想知道怎么用，看 [`../README.md`](../README.md)。

---

## 1. 为什么按「信息源」排序，而不是统一抽帧

核心观察：**同样一份信息，用不同媒介读的成本差一个数量级。**

| 信息 | 文本形式 | 图片形式 |
|---|---|---|
| 一句台词 | ~10 token | 一张字幕带图 ~1000 token |
| 一个关键画面 | 无法表达 | ~300 token（拼图里一格） |

所以顺序是：**能读文本就不读图，必须读图就拼在一起读。**

这不是「优化技巧」，是成本结构决定的——官方字幕 12410 字约 12410 token，而 40 分钟视频按 1fps 抽帧是 60 万 token。

## 2. 取帧：等间隔骨架 + 吸附画面变化点

**只等间隔的问题**：关键画面可能只出现 1~2 秒，等间隔采样会漏掉。

**只吸附关键帧的问题**：转场往往集中在开头/高潮，中段会大量空档。

**混合方案**：

```
base[i] = 段起点 + (i+0.5) × 段长 / n        ← 等间隔骨架，保证覆盖
每个 base 在 ±半格内找 scene_score 最高的变化点 → 吸附过去
阈值阶梯 0.3 → 0.15 → 0.08，≥75% 帧吸附成功就停
去重：吸附后相邻帧距离 < 帧间隔×0.4 时退回骨架
```

**双保险**：覆盖靠骨架，关键帧靠吸附。

### 踩过的坑

- **阈值太高**：0.3 档吸附率低时，一度以为「场景检测失效」，实际是这类视频（冲浪、慢节奏）变化点本来就少。
- **去重下限**：最初没有，导致多帧挤在同一秒。
- **三帧吸附同一变化点**：吸附时取「窗口内最强」，多个基准点会指向同一个强变化点——靠去重（`pickTimes` 里的 `minGap`）把后一个退回骨架才解决。

## 3. 字幕带：为什么不用 OCR

**为什么不 OCR**：
- 中文 OCR 在低分辨率、描边、花哨排版下错误率高
- 需要额外依赖（PaddleOCR / RapidOCR 都是几百 MB）
- 多模态模型读字幕带几乎免费（图里已经有字，不需要二次识别）

**为什么切「带」而不是整帧**：
- 字幕只占画面底部 10%，整帧读浪费 90% token
- 竖排 N 行字幕 → 一张图拿到 N 句台词

**怎么定位字幕带（不靠 OCR）**：

```
抽 24 帧 → 每帧算逐行梯度（字幕边缘会产生高频）
→ 跨帧取 30 分位（字幕「每帧都在」→ 低分位也高；画面内容不会稳定在固定行）
→ 找峰值 → 向两侧扩展到阈值以下
→ 高度限制（不超过搜索区 1/4）+ 置信度（字幕区强度 vs 该帧自身）
```

### 踩过的坑

- **抖音式动态字幕**：位置漂移、不是每帧都有 → 检测出的「带」其实是画面内容。加了置信度门槛（<0.5 跳过）。
- **竖屏高分辨率**：阈值扩展会连成 531px 的大块（实际字幕 60px）→ 加高度上限。
- **区间模式**：`--from/--to` 时只采样区间，字幕位置被画面边缘抢走 → 改为**始终采样全片**（字幕位置是视频级属性）。

## 4. 弹幕：为什么它能当信号

**B 站的弹幕密度本身就是内容信号**，而且能看到画面和字幕都没有的东西：

- **热区 = 观众高光**：一条 LOL 视频 01:20-01:30 弹幕密度是平均的 3~5 倍，内容是团战高潮
- **密度低谷 = 低活跃段**：40 分钟视频里低活跃段（广告/过渡）密度只有全片的 31%（观众跳过）

### 为什么要过滤广告弹幕

弹幕里混着「加微信」「私信我」这类垃圾。但**过滤的原则是宁漏勿错**——

踩过三次误伤：
- 「再也不怕**看这**个场面了」→ 被「看+这」规则误判广告
- 「**666**」→ 被「无意义符号」规则误杀
- 「**？？？**」→ 被「纯符号」规则误杀

最终规则只认**完整短语**（加微信、私信我、关注我主页…），并且：
- 数字重复（6666/1111）保留——是梗
- 中文重复（哈哈哈哈）保留——是情绪
- 纯情绪标点（？？？/！！！）保留

51 个测试用例固定了这些边界。

## 5. 密度与张数决策

```
变化率 rate = 显著变化次数 / 秒
rate > 1.2  → 4 秒/帧（快剪/MV/游戏）
rate > 0.5  → 6 秒/帧（vlog/教程）
rate > 0.15 → 9 秒/帧（口播/慢节奏）
else        → 13 秒/帧（静态/录屏）

张数 = ceil(时长 / 帧间隔 / 9)，再被预算封顶，硬上限 12 张
```

**为什么 4~13 秒**：经验值。人眼对「同一场景内的连续动作」可以合并理解，但场景切换必须分开。4 秒/帧在高动态视频里够用，13 秒/帧对静态内容不浪费。

**为什么硬上限 12 张**：108 帧已经是 40 分钟视频的极限（22 秒/帧）。再稀释就没意义了，不如用 `--from/--to` 分段看。

### 踩过的坑

- 多 P 视频用 `view.duration`（全部分 P 总和）算密度 → 应该用 `pages[p-1].duration`
- ~~竖屏 token 低估~~ **2.0 已消除**：图片单价与尺寸无关（Flash 缩放 ~1300×1300，上限 1024 token），竖屏/横屏同价

## 6. 低活跃段：降权而非跳过（2.0）

```
30 秒滑窗算弹幕密度
→ 低于中位数 45% 的连续窗口（≥45s）→ 低活跃段
→ 输出 lowActivitySegments: [{ from, to, lowDensity, sample }]
```

**不是「广告段」**：密度低谷也可能是「纯画面段」「BGM 段」「慢镜头」——fisheye 不知道是不是广告，只知道「观众不互动」。

**处理：降权而非跳过**（设计 05 §7.3）——低活跃段采样密度 ×0.3（`FISHEYE_LOW_ACTIVITY_WEIGHT`），内容段照常。误报只降权（可恢复），完全跳过则是整段删除（灾难性）。降权只在 render 的 algorithm 轨生效；纯文本链路只标布尔 `lowActivity` 给 agent 参考。

**2.0 砍掉了什么**：1.0.29 的「广告段分级（high/low）+ 关键词聚类 + 打点 + 片头 + 消费回溯 + 台词族 + 分区词库 + 语义仲裁」七路，全砍到「density + keywords」两路（0.1 验证：五路零独立命中）。判断「是不是广告」归 agent。

## 7. 不做的事（以及为什么）

| 没做的功能 | 原因 |
|---|---|
| 多模态视频模型（Video-LLaVA 等） | 需要本地 GPU / 大量显存；云端 API 更贵且不可控 |
| 无监督关键帧聚类 | 场景检测已经够用，聚类增加复杂度但收益不明显 |
| 自动生成视频摘要 | 这是 agent 的活，工具只负责「给材料」——摘要质量取决于模型，不该硬编码在工具里 |
| OCR 画面文字 | 字幕带 + 多模态读图已经覆盖；OCR 增加大依赖 |
| 支持 YouTube | 接口层不同（字幕格式、弹幕不存在），但核心逻辑可复用，欢迎 PR |

## 8. 一条经验

**这个工具最值钱的部分不是代码，是那些踩过的坑。**

每次「看起来只是加个参数」的功能（弹幕过滤、字幕带定位），实际都在和一个具体的中文视频生态妥协：动态字幕、刷屏文化、广告话术、B 站接口加密。

设计文档能写出来的「为什么」，都是踩着具体案例改出来的。

## 9. 平台适配器（1.0.0）

核心不直接认 B站：所有输入经 `lib/platforms/` 的适配器解析成统一契约（时长/字幕/弹幕/媒体），
`auto` 只看适配器声明的能力。加平台 = 抄 `lib/platforms/_template/` + 注册表加一行，不动核心逻辑。

## 10. 语义切换点（可选，1.0.0）

embedding + 变点检测识别「话题切换」时刻，零 token 纯 CPU；结果写 manifest 的 `semanticShifts`，
精读建议里作为额外信号（`source: 'semantic'`）。优先用外部 Python CLI（SEMANTIC_CLI）做 embedding 增强；
找不到 python 时降级为纯 JS 词法切分（`lib/semantic-core.mjs`，char-bigram 漂移，1.0.9 起）。
无官方字幕时，转写台词（`transcriptLines`，1.0.10 起）兜底，本地/URL 视频也能切话题。

## 11. 广告信号源可插拔（1.0.10）

广告检测从「一个函数写死七路」拆成「信号源注册表 + 编排器」：

- 七路信号源：弹幕族五路（密度/关键词/打点/片头/消费）+ 台词族两路（字幕关键词/句式），
  各自是 `lib/signals/` 下的纯函数 `detect(ctx, keywords) -> [{ from, to, subAd? }]`。
- 编排器 `lib/signals/index.mjs` 按 `primary`（主信号）/`secondary`（补充）/`subtitle`（台词族）分组跑：
  主信号开了但没产出 → 早退；补充信号只在主信号有产出后参与；台词族独立追加、不参与弹幕族重叠合并。
- 平台通过 `adDetector.signals` 声明开哪些信号、`adDetector.keywords` 换词库（正则对象）。
- 无弹幕平台（本地/URL）开台词族两路，数据来自 whisper 转写的带时间戳台词（`transcript` 参数）。

加新信号 = 在 `lib/signals/` 加一个文件 + 在 `AD_SIGNALS` 注册一行 + 平台在 `signals` 数组声明。
这是把「换轻量分类模型」挂进来的预留点：模型信号源和关键词信号源同为 `detect` 契约，替换即可。

> **2.0 说明**：本章（第 11 章）描述的「七路可插拔」在 2.0 已砍成两路（`density` + `keywords`），见第 13 章。

## 12. agent 参与边界（2.0）

2.0 的定位（[`docs/2.0/00-总纲.md`](./2.0/00-总纲.md)）：**fisheye = 把视频压成「证据 + 成本」，不替 agent 判断。**

三条推论：

1. **用户是 agent，不是人**：AI 读文字便宜、看图像贵——fisheye 把 AI 的成本结构变成工程决策。
2. **判断权归 agent**：判断「哪段是广告 / 哪段重要 / 话题边界」是 agent 的活——它比规则准，而且它本来就要读。
3. **感知层保持机械**：抽帧、拼图、字幕切片没有判断空间，不需要 agent 介入。

落点：

- 类型判定只给「建议」+ `evidence`（判据命中明细），agent 可覆盖（设计 01 §3.5）。
- 情绪只给「量级」+ `top` 样本，不给「兴奋/平淡」结论（设计 03 §5.1）。
- 广告只给「低活跃段（密度低谷）」+「广告词高光（纯线索）」，不做「是不是广告」的判断（设计 05 §7.2）。
- `visualRequest` 是非阻塞的：fisheye 只报「文本证据不足 + 建议轨道 + 成本」，读不读图由 agent 决定（设计 01 §3.6）。

## 13. 广告检测的结构性约束（2.0）

2.0 把广告识别从「替 agent 判断」降级为「给 agent 线索」（[`docs/2.0/05-广告识别.md`](./2.0/05-广告识别.md)），结构性约束：

- **七路砍两路**：只保留 `density`（低活跃段，影响取帧）+ `keywords`（广告词高光，纯线索）。删除 mark/head/buy/sub-keywords/sub-patterns + 分区词库 + 语义仲裁——0.1 验证：五路零独立命中，两路召回 = 七路 = 100%。
- **降权而非跳过**：低活跃段 `w=0.3` 降权（只在 render 的 algorithm 轨），不「完全跳过」——误报只降权（可恢复），跳过是整段删除（灾难性）。
- **结论配证据**：低活跃段给 `sample`（段内 2~3 条弹幕原文），广告词高光给 `text` 原文——让 agent 一眼验证，不照单全收。
- **平台不声明 signals**：平台只声明「能提供什么广告词证据」（`adKeywords`），用哪些信号是 fisheye 的判断（设计 05 §7.5）。
- **manifest schemaVersion 2**：`adSegments` → `lowActivitySegments`，旧 manifest 被明确拒绝。
