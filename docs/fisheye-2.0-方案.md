> 本文取代早先「双轨渲染」版方案——核心变化是**链路顺序**：从"全量读图"改为"成本优先、读帧最后"。

---

## 一、定位

**fisheye = 把视频压成「证据 + 成本」，不替 agent 判断。**

三条推论：

1. **用户是 agent，不是人。** 人类看图像便宜、读文字贵；AI 读文字便宜、看图像贵。fisheye 把 AI 的成本结构变成工程决策。
2. **判断权归 agent。** 判断「哪段是广告 / 哪段重要 / 话题边界在哪」是 agent 的活，它比规则准，而且它本来就要读。
3. **感知层保持机械。** 抽帧、拼图、字幕切片没有判断空间，不需要 agent 介入。

## 二、核心：成本优先链路（本次最大的改动）

### 2.1 旧链路的问题

按"信息完整性"排：字幕全文 → 弹幕 → 画面 → 精读。结果是**每样都读**：

| 40 分钟视频 | 旧链路 |
|---|---|
| 字幕全文 | 49,757 token |
| 拼图 38 张 | 45,600 token |
| **合计** | **~95,000 token** |

### 2.2 新链路：按成本排，读帧最后

```
① 段卡片（~80 token/段）       ← 先读：每段有什么证据、成本多少
② 字幕骨架（~45~140/段）       ← 不够再读
③ 弹幕高光 + 情绪分（~0）       ← 还不够再读
④ 画面 coarse（~1200/张）      ← 还不够再读
⑤ 画面 fine（~3800/段）        ← 最后手段（agent 点名）
```

| 同一条 40 分钟视频 | 成本优先 |
|---|---|
| 段卡片 ×10 | ~800 |
| 字幕骨架 ×10 | ~1,200 |
| 弹幕高光 ×10 | ~0 |
| 帧 | **0（没读）** |
| **合计** | **~2,000 token（省 47 倍）** |

### 2.3 默认不渲染

`auto` 默认**只产文本证据**（段卡片 + 字幕骨架 + 弹幕高光 + manifest），画面只在 agent 显式请求时渲染。

- 渲染时间：140s → **0**（纯文本 3~5 秒）
- 磁盘：不存 38 张图（省 ~30MB）
- 新增命令：`render --plan plan.json`（按 agent 选择渲染）

### 2.4 跳步（允许，默认顺序不是硬规则）

| 情况 | 跳转 |
|---|---|
| 字幕 `null`/`noisy` | 跳过字幕，读弹幕 |
| 弹幕也 `null` | 直接读 coarse 图 |
| agent 觉得某段重要 | 直接点名 fine |

manifest 每段给 `evidence` 与 `suggestedOrder`（按可用性算出的建议顺序）。

## 三、证据体系：三源 × 可用性 × 画面三轨

### 3.1 证据矩阵

| 证据源 | 便宜档 | 昂贵档 | 缺失时 |
|---|---|---|---|
| 字幕 | 骨架（~45~140/段） | 全文（~5k/段） | `null` |
| 弹幕 | 情绪分 + 高光（~0） | （原始列表，可选） | `null` |
| 画面 | **coarse**（稀疏均匀，~1200/张） | **fine**（5x5，~3800/段） | 不存在（最终兜底） |

### 3.2 核心原则：null ≠ 0，缺失要给置信度

```js
{
  subs:    { source: 'official'|'transcript'|'band'|'none', chars, charsPerMin, quality, confidence },
  danmaku: { available: true|false, count, perMin, confidence },
  frames:  { coarse: { cost }, algorithm: { cost }, adaptive: { cost, enabled } }
}
```

- 没有弹幕 → `danmaku: null`（不是 `emotion: 0`）
- 弹幕 <20 条 **或** <0.05 条/s → `confidence: 'low'`（两个维度：绝对量不足统计不可靠；密度不足同理）
  > 实测：15s 萌宠视频 8 条弹幕 = 0.53 条/s（密度不低）但绝对量只有 8 条——按密度判会通过，按绝对量判才是 low。
- 单段弹幕 <5 条 → 该段 `danmaku: null`，其他段正常
- 字幕 <20 字/分钟 → `sparse: true`
- **`none`（本来就没有）vs `error`（该有但失败了）必须区分**：前者是证据缺失（正常降级），后者是故障（agent 应知道"是网络/API 问题，不是视频没字幕"）
- 字幕 `quality: 'noisy'`（♪ 噪声/重复行）→ 标注警告

### 3.3 降级链

```
① 字幕有（官方/转写质量 OK）→ 读骨架（全文按需）
①b 转写质量差（实词比低）→ **继续尝试字幕带**，不跳过（见字幕链路文档 3.1.1 实测）
② 字幕 null/低置信 → 弹幕有 → 读情绪 + 高光
③ 弹幕也 null/低置信 → 两源都低置信 → 进入「视觉授权」流程（见 3.6）
④ 已授权 → 读 coarse 或 adaptive；agent 点名 → fine
```

**coarse 永远在**——只要 ffmpeg 能解码。连它都失败 = 视频坏了，是错误不是降级。

### 3.4 画面三轨

| 轨 | 抽帧策略 | 用途 | 触发 |
|---|---|---|---|
| **coarse** | 4 分钟/帧（1~2 张 / 40 分钟），3x3，等间隔，不吸附不降权 | 兜底筛查 | 永远可用 |
| **algorithm** | 等间隔 + 单档吸附（score≥0.3）+ 低活跃降权（w=0.3） | 默认路径 | 有字幕/弹幕 |
| **adaptive** | **按视频类型定制密度**（见 3.5） | 无文本证据的视频 | 两源低置信 + 授权 |

> coarse 就是现有 `local` 命令的行为（均匀抽帧拼一张图）——零新增代码。
> adaptive 不是"统一稠密"：PPT 每页一张、MV 密抽、录屏稀疏——是"视觉自适应"。

### 3.5 视频类型判定（adaptive 轨的依据，零成本）

只看元数据，不看图：

| 类型 | 判据 | adaptive 抽帧策略 |
|---|---|---|
| `music`（纯音乐/MV） | 字幕全是 ♪/歌词 + 变化率 >1.2/秒 + 弹幕少 | 按变化率密抽（2~4 秒/帧） |
| `slides`（PPT/演示） | 变化率 <0.05/秒 + 字幕少 + 画面静态 | **每页一张**（场景切页去重） |
| `screen`（无声录屏） | 无音频流 或 平均音量 < -50dB | 30~60 秒/帧 |
| `foreign`（外语无翻译） | 官方字幕语言非中文 + 无翻译轨 | 字幕带优先，帧数按字幕带 |
| `unknown` | 都不中 → 默认 coarse 2 张 | 先扫一眼再决定 |

判定输出：`{ type, confidence }`（0~1，基于判据命中数）。

### 3.6 视觉授权：三档配置（`on` / `off` / `ask`）

```json
// ~/.config/fisheye/config.json
{ "visualTrack": "ask" }
```

```bash
FISHEYE_VISUAL_TRACK=on node fisheye.mjs auto BV1xxx   # 环境变量覆盖
```

| 档位 | 两源低置信时 | 渲染 |
|---|---|---|
| **`on`** | 类型判定命中且 `confidence ≥ 0.7` → **直接开启 adaptive 轨**（按类型密度） | 自动 |
| **`off`** | 永不开启 adaptive 轨 | 不渲染 |
| **`ask`**（默认） | 只标记 `visualRequest`（类型 + 建议帧数 + 成本） | **不渲染，等授权** |

**授权是非阻塞的**——fisheye 的调用方是 agent，永远不 `readline` 等输入：

```json
{
  "visualRequest": {
    "reason": "no-subs-no-danmaku",
    "type": "slides",
    "confidence": 0.8,
    "suggestedTrack": "adaptive",
    "suggestedFrames": 6,
    "costEstimate": 7200
  }
}
```

- agent：看到 `visualRequest` → 调 `render --plan plan.json`（选 adaptive / coarse / skip）
- 人类（TTY）：stdout 打一行提示 + 建议命令（不等待）

**`on` 档也要求 `confidence ≥ 0.7`**——类型不确定时降级为 `ask`，避免"类型猜错 + 自动密抽"浪费 token。

### 3.7 低置信拼图

把"算法没把握"的帧集中打包成一张带时间戳的图，让 agent 花一张图的成本扫完全部可疑段：

```
主网格（置信帧）      ← 看"有什么"
低置信拼图（9 格/张）  ← 扫"有没有漏"（每格左上角标时间戳）
精细帧               ← 看"细节"
```

低置信帧定义：骨架帧（未吸附）+ 低活跃段帧 + 低变化率段（<0.05/秒且无弹幕高光）的帧。

收益：主网格更干净（不被低置信帧挤占）+ 低置信段可被判断（不再浪费）。净成本 +1200 token/张。

### 3.8 按段并置（证据对齐 vs 判断的边界）

证据**按段并置**，不做全局并列——因为"按时间戳对齐"是机械工作，属 fisheye；"这些证据加起来意味着什么"是判断，属 agent。

```json
段 4  12:00-16:00
  subs:        { head, keywords, op, confidence }
  danmaku:     { emotion, hits, confidence }
  adHits:      [{ t, text }]          ← 广告词命中，同段并置
  lowActivity: false
  shifts:      []
  needsFrames: false                   ← 两源都低置信时 true
  frames:      { coarse: { cost }, adaptive: { cost } }
```

agent 读到"这段在评测一加手机 + 观众在刷'商单'"——上下文就在眼前，自己判断是调侃还是广告。**fisheye 不做这个判断。**

## 四、字幕链路（详见 `docs/字幕链路-设计.md`）

### 4.1 摘要四铁律（实测校准）

| 规则 | 不遵守的后果 |
|---|---|
| 关键词用 **TF-IDF**，不用词频 | 每段都抽出全片高频词（`grain/were/had`） |
| 停用词表完整（英文 200+，中文 200+） | `were/had/after/得到/苏联的` 漏进关键词 |
| **广告句踢出摘要** | 抽到广告口播（"Oil Control 洁面产品"） |
| head/info 截断 60 字（中）/110 字符（英） | 每段 170~200 token（截断后 90~140） |

### 4.2 摘要形态

```js
{
  fact:    "1972年苏联一把抄走美国1/4小麦产量",   // 事实句
  op:      "那都不是祖坟冒青烟，那是祖坟核聚变",    // 观点句（作者态度，可空）
  keywords, numbers, claims, head, info
}
```

**事实与观点分两条通道**——梗句承载观点，不是噪声（实测：段 5 的吐槽句评分最高，确实是该段信息密度最高的句子之一）。

### 4.3 轨与翻译

- 有翻译轨 → 抽中文摘要（49,757 → 11,615 → 摘要 ~1.1k/9 段）
- 无翻译轨 → 英文摘要（关键词/术语保留原文）
- **翻译不进 fisheye**（下游化：B站 轨 / agent 自己 / 人用翻译软件）
- 全文按段落盘（`seg-NN-subs.txt`），summary 只给决策，全文给引用

### 4.4 已知缺陷

中文无分词器时用 3~4 字窗口 + 去重叠，仍会拆词（「迪亚科夫」→「迪亚科/亚科夫」）。可接受——索引只用于决策。

## 五、弹幕链路：情绪双分数

### 5.1 两个分数（不给判定）

```js
{
  subsEmotion:    0.033 | null,   // 每句情绪词数
  danmakuEmotion: 0.052 | null,   // 情绪弹幕占比
  confidence:     'ok' | 'low' | 'none'
}
```

### 5.2 必须用分位数，不用绝对阈值

实测：可汗视频 10 段，中位数 `字幕 0.009 / 弹幕 0.071`——按 0.5 阈值判定会全部"都低"。必须与全片中位数比较（相对高低）。

### 5.3 耦合映射（实测修正）

| 状态 | 含义 | 建议 |
|---|---|---|
| 都高 | **高潮段**（UP 激动 + 观众激动） | 两源都看 |
| 字幕高 / 弹幕低 | UP 在玩梗，观众冷静 | 看字幕（观点在字幕） |
| 弹幕高 / 字幕低 | 观众在嗨，内容在讲事实 | 看字幕（事实在字幕） |
| **都低** | **平淡段**（过渡/铺垫） | 可降权 |

> **"不重要"的判据是"都低"，不是"都高"**——实测段 8（1972 大收购，全片最重要内容之一）就是"都高"。

## 六、语义：保留外挂，默认纯 JS

- 默认：纯 JS 词法（`lib/semantic-core.mjs`，零依赖零 token）
- 外挂：`SEMANTIC_CLI` 契约（stdin JSON → stdout JSON），可接 fastembed / 本地小模型 / 云端 LLM
- **推荐本地小模型**（3B~7B）：免费、离线、窄任务（切分/分类）够用
- 不推荐云端 LLM（贵），也不让 fisheye 做"摘要/总纲"（那是判断）
- 切分错误容错高（agent 能自愈），但 manifest 要标 `boundary: { source, confidence }`
- 切点吸附到句子边界（一行代码），广告段优先整段保留

## 七、广告：两路 detect + 广告词高光

| 保留 | 删除 |
|---|---|
| `danmaku-density`（低活跃段） | `mark`（数字打点） |
| `danmaku-keywords`（广告词） | `head`（片头强信号） |
| 广告词高光 `adKeywordHits`（纯线索） | `buy`（消费回溯） |
| — | `sub-keywords` / `sub-patterns`（台词族，依赖字幕质量） |

- `subtractAds`（完全跳过）→ `weightSegments`（低活跃段降权 w=0.3，`FISHEYE_LOW_ACTIVITY_WEIGHT`）
- **广告句过滤复用 `adKeywordHits`**：字幕摘要用它剔除广告口播（同一个信号两个用途）
- 平台适配器不再声明 `signals`（只声明"能提供什么证据"）

## 八、设计目标：纯文本可用

> **默认输出不依赖任何视觉能力**；画面只在显式请求时渲染。文本模型能完成"了解 + 筛选"，视觉模型负责"精读"。

两阶段架构：

```
阶段 1：纯文本模型（便宜）→ 读段卡片 + 字幕骨架 + 弹幕 → 筛出值得看的段
阶段 2：视觉模型（贵）    → 只读被筛出的段的 fine 帧
```

纯文本模型的盲区是**可预测的**（证据可用性链会明确标出"字幕 null / 有 38 张图没读"），所以它知道自己的边界，不会硬猜。

## 九、工作流：主 agent / 子会话 / fisheye 三方分工

### 9.1 角色

```
主 agent（上下文宝贵，判断强）
  ① fisheye auto → 拿段卡片（~2k token）
  ② 判断：这视频值不值得细看？哪几段？
  ③ 派子会话（带 manifest + 选中段 + 允许的轨道）
  ④ 只拿结论（~500 token）

子会话（独立上下文，模型可以更便宜）
  ① 读段卡片 + 骨架
  ② 请求 render（coarse/fine）→ 读图
  ③ 需要细节 → 读 seg-NN-subs.txt 全文
  ④ 产出结构化复述（时间戳 + 要点 + 结论）

fisheye（感知层，不做判断、不派单）
  段卡片 / 骨架 / 弹幕 / 三轨渲染 / manifest
```

### 9.2 三层成本（证据分档 → 模型也分档）

| 层 | 谁做 | 模型档 | 成本 |
|---|---|---|---|
| 判断 | 主 agent | 强（贵） | 读卡片 ~2k token |
| 读证据 + 复述 | 子会话 | **便宜**（flash/mini 级） | 读图/全文（token 多、单价低） |
| 感知 | fisheye | 无模型 | 渲染/抽取（零 token） |

关键：**读图/读全文是"上下文重、判断轻"的活**，适合便宜模型；判断"哪段值得读"才是强模型该干的。

### 9.3 派发阈值

| 情况 | 派子会话？ | 理由 |
|---|---|---|
| 短视频（<2 分钟）+ 证据少 | ❌ 主 agent 自己读 | 派单开销 > 收益 |
| 长视频（>10 分钟）+ 要读多张图 | ✅ 派 | 读图 token 大 |
| 字幕全文要读 5k+ token | ✅ 派 | 同上 |
| 只需看 1 张 coarse | ❌ | 主 agent 直接读 |

经验阈值：**"要读的量" > 3k token 才值得派**。

### 9.4 输出契约（强制引用，防编造）

```json
{
  "segments": [
    { "i": 3, "summary": "...", "points": [{ "t": "12:34", "text": "..." }] }
  ],
  "unknown": ["12:40 画面看不清"]
}
```

- 每个要点**必须带时间戳引用**（有引用就难编）
- 允许 `unknown`：看不到就如实说
- 主 agent 抽查 1~2 个关键点回读原文/图（贵但只读一点）

### 9.5 落点

- **fisheye 不参与编排**（只出证据和成本）
- 编排在 agent 层（DSH subagent / 插件 / 主 agent 自己）
- 可给参考 prompt 模板，但不写死

## 十、性能优化：把三轮解码合成一轮

### 10.1 现状（40 分钟视频，实测）

| 阶段 | 耗时 | ffmpeg 调用 |
|---|---|---|
| 下载 281MB | 227s | — |
| 场景检测（全片 320p 解码） | 72s | 1 |
| 抽帧（108 帧，逐帧 seek） | 140s | ~108 |
| **合计** | **~370s** | **~120 次** |

### 10.2 五条优化（按收益）

| # | 优化 | 收益 | 代价 |
|---|---|---|---|
| **①** | **场景检测与抽帧共享一次解码** | −70s（省一整遍全片解码） | 重构 detectScenes + pickTimes 的调用方式 |
| **②** | **流式管线**：下载 → 检测 → 抽帧合成一条 ffmpeg | 重叠约 60s | 需要分片输入或 pipe |
| **③** | **批量抽帧**：一次调用输出所有帧（select 表达式） | −40~50s（108 次进程启动 → 1 次） | 重构抽帧实现 |
| **④** | **两段式下载**：先下 320p 做检测/字幕/弹幕，高清只下精读段 | 227s → ~50s | 复杂度高（高清段 seek / 对齐） |
| **⑤** | **场景检测跳帧 + 降采样**：每 0.5s 一帧 + 160p（现在逐帧 320p） | 72s → 15~25s | 变化率精度略降（4/6/9/13 秒阶梯不需要逐帧精度） |

**①③⑤ 先做**（纯重构，精度不降）；**②④ 后做**（流式/两段式，复杂度高）。

### 10.3 预期效果

| 项 | 现在 | 优化后 |
|---|---|---|
| 40 分钟视频总耗时 | ~370s | **~150s** |
| ffmpeg 调用次数 | ~120 | **~3** |
| 精度损失 | — | 无（①②③） / 小（④ 用 320p 检测） |

### 10.4 顺带的小优化

- **字幕带采样复用**：band 检测的 24 帧可与 coarse 抽帧共用
- **JPEG 质量 85 → 75**：视觉无差，磁盘省 ~30%
- **渲染缓存键**：按 (时间戳, 网格, 分辨率) 缓存，coarse/fine 同帧不重复渲染
- **段卡片去重**：公共字段（标题/时长/源）放 manifest 顶层，段卡片只放段级字段
- **adKeywordHits 共用**：字幕摘要过滤与段卡片命中共用一份计算
- **mp4 缓存只留 320p**：两段式下载后，高清段用完即删，只留 ~30MB 的检测副本（原 235MB）
- **manifest 时间戳精度**：2 位小数 → 1 位（渲染时仍用高精度，只影响 manifest 体积）

### 10.5 核实：场景检测没有重复执行

曾怀疑 `stageAuto` 里场景检测跑了两遍（collect 一次 + stageGrid 一次），实际核查：

```js
// stageGrid
const visualScenes = pre.scenes ?? detectScenes(mp4)   // 有 pre.scenes 就不重跑
```

`stageAuto` 把 `collectSignals` 算好的 `scenes` 通过 `pre` 传下去——**只跑一遍**。这是"共享解码"优化（①）的前提：现在的瓶颈不是重复检测，而是"检测一遍 + 抽帧 108 次 seek 各开一次解码"。

### 10.6 API 响应缓存

| 数据 | 会不会变 | 缓存策略 |
|---|---|---|
| `view`（标题/时长/cid/tid_v2） | 几乎不变 | 永久 |
| `subtitles`（主轨 + 翻译轨 JSON） | 几乎不变 | 永久 |
| `danmaku`（弹幕列表） | **会增长** | 短期（1 小时） |

```json
// cache/api/<id>.json
{
  "view":      { "data": {...}, "at": 1763... },
  "subtitles": { "data": {...}, "at": 1763... },
  "danmaku":   { "data": [...], "at": 1763... }
}
```

- **一个文件 + 分块时间戳**：一次读写；各块独立过期（弹幕过期只重取弹幕）
- **缓存全量、用时过滤**：`--from/--to` 时不缓存"过滤后的结果"，否则之后要全片会不完整
- `--refresh` 强制全部重取
- 与产物缓存（out/ + mp4）互不干扰：API 命中不发请求，产物命中不渲染

### 10.7 懒加载 optional 模块

`fisheye.mjs` 现在 import 全部模块（audio 535 行 / ocr 294 / ytdlp 284），大部分命令用不到。改成按需 `await import()`：启动快 ~50ms，副作用小；`selftest` 需要全部时再加载。
### 10.8 时间预算（`--max-seconds`）

`--budget` 管 token，但 agent 还要管**时间**：40 分钟视频全链路 150s，agent 可能只愿意等 30s。

```
--max-seconds N
  → 超时不是报错，而是「降级到纯文本链路」（3~5s，不渲染）
  → 先给段卡片/骨架/弹幕，图等 agent 后续再要
```

比"超时报错"好：**先给能给的证据**，图随时可以补。

## 十一、人类自检产出：一个 report.html 作为唯一入口

### 11.1 问题

2.0 默认不渲染、只产文本证据（给 agent）——对人类来说这是黑盒。而且人类要看的东西原本散在 4 个地方（stderr / report.md / manifest / trace），找一个信息要翻几个文件。

### 11.2 集合到一个 report.html

```
out/<id>/
  report.html        ← 人类唯一入口（全部信息）
  inspect.jpg        ← 自检图（report.html 内嵌/链接）
  manifest.json      ← agent 看
  trace.json         ← 调试（FISHEYE_TRACE=1）
```

report.html 的区块：

| 区块 | 内容 |
|---|---|
| 概览 | 标题 / 时长 / 平台 / 耗时 / token 估算 / 成本 |
| 证据可用性 | 字幕（source/置信度/理由）、弹幕（条数/密度）、画面（是否读过） |
| 段列表 | 每段：时间 / 字幕骨架 / 弹幕情绪 / 低活跃 / needsFrames / 判定理由 |
| 自检图 | inspect.jpg（1 张 coarse + 时间戳），点开看大图 |
| 诊断 | 判定理由（为什么 low/none）、降级链走到哪一步 |
| 链接 | manifest.json / trace.json / 各段产物 |

### 11.3 为什么 HTML 而不是 md

| | md | html |
|---|---|---|
| 看图片 | 要单独打开 | 内嵌，一眼看全 |
| 表格 | 可以 | 可以（可折叠） |
| 分享 | 一般 | 直接发文件 |
| 生成成本 | 零 | 零（字符串拼接） |

零 token 成本，人类体验差一个数量级。

### 11.4 单文件 vs 多文件

| 方式 | 优点 | 缺点 |
|---|---|---|
| 多文件（report.html + 相对路径图） | 生成快、文件小 | 发出去要带整个目录 |
| 单文件（图 base64 内嵌） | 发一个文件就行 | 图多时文件大（38 张 → 30MB+） |

默认多文件（本地看），`--report-single` 时内嵌（分享用）。

### 11.5 三层自检

| 层 | 产出 | 用途 | 默认 |
|---|---|---|---|
| L1 | report.html | 报告 + 段列表 + 判定理由 | ✅ |
| L2 | inspect.jpg（1 张 coarse + 时间戳） | 一眼看全片 | `--inspect` |
| L3 | seg-NN-fine.jpg | 看某段细节 | `render --segments N` |

### 11.6 批量：两级索引（agent 看 JSON，人看 HTML）

```
out/index.json          ← 视频级索引（每视频 ~50 token：标题/时长/字幕/弹幕/推荐）
out/index.html          ← 同上的人类视图
out/<id1>/manifest.json ← 段级卡片
out/<id1>/report.html   ← 段级的人类视图
```

agent 读 index.json 选视频 → 读 manifest.json 选段 → 读轨道证据。

### 11.7 输出归属：stdout 给 agent，stderr 给人

| 流 | 内容 | 谁读 |
|---|---|---|
| stdout | `MANIFEST: ...` / `visualRequest: {...}` / `SHEET: ...` | agent（重定向时只拿这个） |
| stderr | 规划报告 / 进度 / 提示 / 警告 | 人类（终端） |

逻辑：人类直接跑时两个流都显示在终端（体验不变）；重定向时 agent 只拿 stdout（不混日志）。

### 11.8 为什么必须默认产出

- **零成本**：纯文本拼接，几 KB
- **人类唯一的黑盒出口**：没有它，人类无法确认"是不是抽错了、字幕为什么没读到"
- **诊断价值**：判定理由（为什么 low/none）是人排障的第一入口

## 十二、成本报价（报价而不是规划）

### 12.1 为什么从"规划"改成"报价"

1.0.29 的预算规划（密度/张数/降级/精读预扣）是**替 agent 取舍**，和"判断归 agent"冲突。2.0 改为：fisheye 只**报价**，agent 决定买什么。

### 12.2 计费基准：DSV4.1 Flash（我们自己用的模型）

公开规则（DeepSeek 官方）：**每张图最多 384 token**，图片自动缩放到约 800×800，**与原始尺寸无关**（实测 800×800 与 3000×3000 同为 348 token）。

但**"每图 384"是 Flash 自己的规则，不是通用规则**——其他模型按 tile / 像素 / 固定值计费，偏差方向和幅度都不同：

| 模型 | 单图实际 | 对常量 1200 的偏差 |
|---|---|---|
| **DSV4.1 Flash** | ~348 | 高估 **3.4×** |
| Gemini | ~258 | 高估 4.7× |
| GPT-4o | ~1105 | 略高估 1.1× |
| Claude | ~1600 | **低估 0.75×** |
| Qwen-VL | ~1300 | 略低估 0.9× |

所以常量 `1200` **不是"错"，而是"只对 GPT-4o 类模型对"**——必须按模型换算：

```
单张成本 = 基准（flash 348）× 该模型图片倍率
```

> 推论：「竖屏 3 倍」的假设对 Flash 作废（自动缩放让尺寸无关）；对其他按 tile 计费的模型仍部分成立。

### 12.3 基准（可量化、不含优化技巧）

| 基准 | 定义 | token（DSV4.1 Flash） |
|---|---|---|
| `perFrame` | 1 fps 逐帧独立输入：2400 帧 × ~348，**不拼图** | **~835,000** |
| `fullSubs` | 全读官方字幕 49,757 字（不压缩） | ~49,757 |

> 基准必须写明"不拼图"——拼图法的成本取决于网格/单价/面积修正，变量太多不可量化，不能当基准。

### 12.4 其他模型按倍率倒推

| 模型 | 单图上限 | 倍率（vs Flash） | 对 1200 常量 |
|---|---|---|---|
| **DSV4.1 Flash** | ~348 | **1.0**（基准） | 高估 3.4× |
| Gemini | ~258 | 0.74 | 高估 4.7× |
| GPT-4o | ~1105 | 3.2 | 接近 |
| Claude | ~1600 | 4.6 | 低估 0.75× |
| Qwen-VL | ~1300 | 3.7 | 接近 |

**图倍率与文倍率分开**：图片按"单图上限"制（倍率差异大），文本按字符 tokenize（倍率 0.8~1.0，差异小）。

### 12.5 报价单形态

```json
{
  "quote": {
    "imageModel": "flash",
    "confidence": "high",
    "baseline": {
      "perFrame": { "token": 835000, "desc": "1 fps 逐帧独立输入，不拼图" },
      "fullSubs": { "token": 49757, "desc": "全读官方字幕" }
    },
    "text":   { "abs": 2000 },
    "coarse": { "rel": 0.17 },
    "fine":   { "rel": 0.85, "per": "段" }
  }
}
```

- **agent 侧**：一个 `abs` 锚点（text）+ 各项 `rel` 比例——够它排序和算总价
- **文本也有倍率**（`textFactor`）：字幕 49,757 字在 DeepSeek ≈ 49,757 token，在 GPT-4o ≈ 30k~35k（中文 0.6~0.7 字/token）——报价的 `abs` 按当前配置模型的 `textFactor` 换算
- **人类侧**（report.html）：全部绝对数 + 费用估算（**统一按闲时单价**，注一行"高峰时段 ×2"，不展开时段细节——时段只影响钱，不影响 token 总量）
- **缓存命中**：报价标 `cached: true` → 重跑成本 ≈ 0（DSV4.1 Flash 缓存命中 $0.003/1M，比输入便宜 50 倍）

### 12.6 读图模型由人类配置（`imageModel`）

```json
// ~/.config/fisheye/config.json
{
  "imageModel": "flash",         // 读图用的模型（可选，默认 flash）
  "readerImageFactor": 2.0,      // 高级：相对 flash 的图片倍率
  "defaultBudget": 5000          // 可选：不填 = 不限制
}
```

两个模型要分清：

| 证据 | 谁读 | 模型 |
|---|---|---|
| 文本（骨架/卡片/全文） | 主 agent | 主 agent 的模型（fisheye 不管） |
| 图片（coarse/fine） | 子会话 | `readerModel`（配置） |

`imageModel` 指**读图那一步用的模型**——不管它是子会话读还是主 agent 自己读，都填这个。文本差异小，用 `textFactor` 单独覆盖。

### 12.7 未知模型的三层退路

| 情况 | 处理 | 标记 |
|---|---|---|
| 已收录（flash/gemini/gpt/claude） | 用倍率表 | `confidence: 'high'` |
| 未收录（新模型/中转） | 回退 flash 基准 | `confidence: 'low'` + "可能偏差 3 倍" |
| 自定义倍率 | 用 `readerImageFactor` | `confidence: 'user'` |

**未知模型 = 估算 + 标注，不报错**。本地小模型（Qwen2.5-VL / LLaVA / MiniCPM-V）的图片计费取决于推理引擎（llama.cpp / vLLM / Ollama 不同），没有统一标准——文档说明"按实际引擎实测填倍率"。这类用户有技术基础，最小支持即可。

### 12.8 预算三级（默认零配置）

| 层 | 行为 | 谁用 |
|---|---|---|
| 默认 | **不设硬预算**，只报价 | 大多数人 |
| `--budget N` | **报价上限提示**（超了标 `budgetExceeded: true`，不硬截断） | 临时控制 |
| `defaultBudget`（配置） | 全局默认预算 | 高级用户 |

默认不限制是故意的：agent 自己知道上下文剩多少，不需要 fisheye 替它管。
`--budget` 也不是硬截断——超了只标记，让 agent 自己决定砍哪项（因为渲染是它按需请求的，fisheye 截不了）。

### 12.9 guidance：最高前提 + 执行顺序

```json
{
  "guidance": {
    "top": "最高前提：在能回答问题的前提下，用最少的 token。能从 text 回答就不要买图；能从骨架回答就不要读全文；能只看 1 段就不要看 3 段。",
    "steps": [
      "默认先读 text（~2k）——大多数问题这一步就够",
      "text 不够才买 coarse（~0.17×）",
      "fine 只买确定要细看的段（~0.85×/段）"
    ],
    "source": "报价按 readerModel=flash 计算（图片 ~348 token/张）；模型不同按倍率换算"
  }
}
```

`top` 的目标函数（最小化 token），`steps` 是执行顺序，`source` 是数据来源说明。
## 十三、agent 侧使用指南（skill 形态）

### 13.1 为什么要有这个

报价单只给价格，不教"怎么花"。skill 把"怎么花"写成流程，所有 agent 复用一份。

### 13.2 证据档位表（三源 × 三档）

| 证据 | 档 1（默认） | 档 2（更细） | 档 3（最贵） |
|---|---|---|---|
| 字幕 | 骨架（~45~140/段） | 全文（~5k/段） | 字幕带图（~348，无文本时兜底） |
| 弹幕 | 情绪分 | 高光列表 | 原始弹幕（可选） |
| 画面 | coarse（~348） | algorithm（默认渲染档） | adaptive / fine（~348/段） |

注意两个轴不同：
- **画面三轨**是密度维度（一张图放几帧）
- **字幕三档**是形态维度（压到多细：骨架 → 全文 → 图）

### 13.3 三层流程

```
① 先看有没有   各源档 1：骨架 / 情绪分 / coarse
② 不够再细     档 2：全文 / 高光 / algorithm
③ 最后才是图   档 3：字幕带 / adaptive / fine
```

第 ③ 层是否可用，取决于 `visualTrack` 配置（见 13.6）：
- `on` → adaptive 已自动生成
- `ask`（默认）→ 只有 `visualRequest` 标记，需要你决定
- `off` → 没有 adaptive，只能 coarse/fine

### 13.4 三轨怎么选（画面）

| 问题 | 轨道 |
|---|---|
| 这视频讲什么 | text（2k） |
| 画面里大概有什么 | coarse（1 张） |
| 某段画面细节/文字 | fine（该段） |
| 无字幕无弹幕 | 授权后 adaptive（PPT 每页 / MV 密抽 / 录屏稀疏） |
| 有字幕弹幕时的默认 | algorithm（auto 已算好，agent 不用手动选） |

### 13.5 fine 的准入门槛（硬约束）

**三条全满足才买 fine，否则不买：**

1. **问题需要画面细节**：文字/数字/图表/动作，且 text 与 coarse 都答不了
2. **只需要 1~2 段**，不是全片
3. **能说出"要看哪一段的什么"**——说不出就是没想清楚，不买

**fine 不是"更准"，只是"更细"**：
- fine 提高的是分辨率，不改变"这段讲什么"——那是 text 的事
- 指望 fine 更准，是拿它做它不擅长的事（语义理解）

**"保险"不是买 fine，是买 coarse**：
- coarse 一张覆盖全片（348），用来确认"有没有东西"
- fine 是精确（348/段），用来回答"这个细节是什么"
- 两者不是"粗细"的区别，是"覆盖"vs"精确"的区别

### 13.6 收到 `visualRequest` 怎么办（取决于 `visualTrack` 配置）

`visualTrack` 是人类配的三档，决定"两源低置信时 fig 要不要图"：

| 档位 | fisheye 的行为 | agent 该做什么 |
|---|---|---|
| `on` | 类型判定命中且 confidence≥0.7 → **自动开 adaptive** | 什么都不用做，图已经有了 |
| `ask`（默认） | 只标记 `visualRequest`（类型/建议帧数/成本），不渲染 | **agent 决定**：值得看就 `render --track adaptive`，不值得就忽略 |
| `off` | 永不开启 | 没有 adaptive 可买，只能 coarse/fine |

**`visualRequest` 不是必须响应**——它是"我这边没文本证据了，要不要看图你定"，不是"快给我授权"。

判断标准同 fine 的门槛：问题真需要画面 → 授权；只是想"保险" → 忽略（或买 coarse）。

### 13.7 反例（别这样）

- 问"这视频讲什么"却直接买 fine（浪费 5 倍）
- 不确定就全买（预算爆炸）
- **把 fine 当"更准"的必选项**（它是"更细"，不是"更准"）
- **为了"保险"买 fine**（保险该买 coarse）
- 买 fine 却说不出"要看哪段的什么"（没想清楚就买）
- 把报价里的数字当"必须花完的预算"

### 13.8 报价怎么读

- `text` / `coarse` / `fine` 是**单价**
- `allIn` 是全买总价（**不是推荐**）
- `fitsWhat` 是"预算内能买什么"（给过 budget 才有）
- **没有"套餐"**——自由组合；上面的流程是建议，不是必选

### 13.9 落点

| 位置 | 用途 |
|---|---|
| `dsh-plugin/skills/fisheye.md` | DSH 插件用户自动加载 |
| `docs/USAGE.md` | 其他 agent 自行读取 |
| MCP tool description | 只放最简版（几句话） |
## 十四、不做的事（明确边界）

| 不做 | 理由 |
|---|---|
| 外部翻译接口 | 收益几十 token，维护永久；用「输出 JSON 可 pipe」代替 |
| LLM 摘要/总纲 | 判断层，归 agent |
| 五路广告 advice 双轨制 | 降级比删除难；27 条真值没证明价值 |
| 云端 LLM 语义切分 | 贵；本地小模型够用 |
| 摘要覆盖率保证 | 抽取式必有遗漏，全文落盘兜底 |
| 分词器（为了关键词可读） | 索引只用于决策，破零依赖不值 |
| 插件生态 | 单人维护不起「平台 × 信号」参数面 |

## 十六、验收标准

| 项 | 标准 |
|---|---|
| 文本链路成本 | 40 分钟视频 ≤ 3k token（卡片 + 骨架，零帧） |
| 默认不渲染 | `auto` 不生成任何 jpg；`render` 才生成 |
| 纯文本可用 | 文本模型能回答"这视频讲什么、哪段值得细看" |
| 三轨 | coarse 永远可跑；algorithm 默认；adaptive 只在两源低置信 + 授权后 |
| 授权三档 | on 自动开（仅 confidence≥0.7）、off 不开、ask 只标记不渲染 |
| 缺失处理 | 无字幕/无弹幕时 `null` + `confidence: 'none'`，不出现 `0` |
| 摘要质量 | 每段 head 能独立说明段落内容（人工抽检 5 条） |
| 广告召回 | 两路 ≥ 六路基线的 80%（否则退回折中） |
| 性能 | 纯文本链路 <5s；coarse 单张 <10s |
| 测试 | 全量通过（242 → 约 250） |
