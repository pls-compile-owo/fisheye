# 0.5 计费基准核对记录（第 0 批验证）

> 核对时间：2026-11-18。结论：设计文档 09 的图片单价口径已过时，需按官方当前规则重定。
> 用户决策：按官方 1024 上限重新定成本口径。

## 一、结论

设计文档 `09-成本报价.md` 的「**348 token/图、每图上限 384、缩放约 800×800**」来自已退休的
`deepseek-v4-flash-vision-exp`（2026-08-21 上线时的口径）。该模型已并入 `deepseek-flash`，
当前官方规则整体变更，**348 不是 ±10% 内的误差，是模型换代导致的口径更换**。

## 二、官方当前规则（deepseek-flash vision）

来源：[官方 Vision 文档](https://api-docs.deepseek.com/guides/vision#token-usage)、[Token 用量计算](https://api-docs.deepseek.com/quick_start/token_usage)

1. 图片按尺寸转 token，计费与文本 token 合并。
2. 推理前自动缩放：
   - 总像素 < 约 544×544 → 放大（保比例）
   - 更大 → 缩小到总像素 ≈ **1300×1300**
3. 每图上限 **1024 token**；2000×2000 与 5000×5000 消耗相同 token（缩放后一致）。
4. `detail: low` 可降为 512×512 缩放（更便宜）；默认 `original` 走上述缩放。

## 三、旧 vs 新口径

| 口径 | 设计文档 09（定稿，过时） | 官方当前 |
|---|---|---|
| 每图上限 | 384 token | **1024 token** |
| 缩放基准 | ~800×800 | **~1300×1300** |
| 单图实测 | 348 | 待实测（上限 1024） |

## 四、fisheye 拼图实测分辨率 → 必达上限

| 拼图 | 生成参数（stages.mjs） | 分辨率 | 是否达 1300×1300 基准 |
|---|---|---|---|
| 3x3（auto 默认） | `scale=640:-1,tile=3x3` | 1920×1080（≈207 万像素） | ✅ 达上限 1024 |
| 5x5（fine） | 同 scale=640 | 3200×1800（更大） | ✅ 达上限 1024 |
| local 3x3 | `scale=480:-2,tile=3x3` | 1440×~810（≈117 万像素） | ⚠️ 略低于基准，≈700~900 token |

结论：**fisheye 的 3x3/5x5 拼图必然达到 1024 token 上限**，报价按 **1024 token/张** 是安全口径（不会低估成本）。

| 项 | 旧（348） | 新（1024） |
|---|---|---|
| 图片单价 perImage | 348 | **1024** |
| text 锚点 | 2000 | 2000（不变） |
| coarse rel | 0.17 | **0.51** |
| fine rel | 0.17 | **0.51**（/段） |
| adaptive rel | 0.17 | **0.51**（/张） |

## 六、影响面（哪些变、哪些不变）

- **不变**：「默认只读文本省 25~32 倍」这个核心卖点**不变**——它比较的是 text 锚点（2000）vs 旧全读链路（51k~64k），与图片单价无关。
- **变了**：agent **按需读图**的边际成本 ×3（348→1024）。coarse/fine/adaptive/lowconf 的报价、`visualRequest.costEstimate`、`budget.fitsWhat` 都要改。
- **连带**：`09-成本报价.md` 12.2/12.3/12.4/12.5 全部数字、`HANDOFF` 铁律 1 的「348 token/张」、`00-总纲` 里的 348 引用，需在第 4 批统一改成 1024。
